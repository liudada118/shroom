# 项目处理步骤与逻辑说明

> 本文只说明项目运行时“每一步做了什么处理、用了哪些逻辑”。不包含完整 PRD 的背景、目标、用户、发布计划等内容。

## 1. 应用启动与服务初始化

1. Electron 主进程从 `index.js` 启动。
2. 主进程先分配端口，默认包含前端端口、API 端口、WebSocket 端口。
3. 如果端口被占用，会通过 `portFinder` 自动寻找可用端口。
4. 主进程 fork 后端子进程 `server/serialServer.js`。
5. 后端读取环境变量，拿到实际的 API 端口、WebSocket 端口、打包状态、资源路径、下载路径、串口缓存路径。
6. 后端读取加密配置文件 `config.txt`，确定当前系统类型。
7. 后端初始化 SQLite 数据库，并把数据库实例放入全局 `state.currentDb`。
8. 后端启动两个服务：
   - Express API 服务，处理页面按钮和数据请求。
   - WebSocket 服务，向前端推送实时数据、回放数据、连接状态和设备状态。
9. 后端启动成功后，通过 `process.send` 把实际端口回传给 Electron 主进程。
10. 主进程再启动前端页面：
    - 开发模式可启动 Vite dev server。
    - 静态模式加载 `client/build/index.html`，并注入实际端口到 `window.__PORTS__`。

## 2. 系统配置与设备类型处理

1. 页面进入后，通过 API 获取当前系统类型。
2. 系统类型会影响后续矩阵尺寸、设备类型、点阵映射和显示模式。
3. 设备类型主要包括：
   - 坐垫、靠背类矩阵。
   - 床垫类矩阵。
   - 手部、足部、大矩阵等。
4. 后端维护设备类型和矩阵尺寸映射，例如：
   - `endi-back` 使用 50 x 64。
   - `endi-sit` 使用 46 x 46。
   - 常规坐垫、靠背、床垫、手部多为 32 x 32。
   - `bigHand` 使用 64 x 64。
5. MAC 地址和设备类型会写入本地 `serial_cache.json`。
6. 后续再次连接同一设备时，优先读本地缓存，减少重复识别。
7. 如果本地缓存没有设备类型，再尝试走在线识别或用户配置。

## 3. 串口连接与设备识别

1. 用户点击连接后，前端请求 `/connPort`。
2. 后端进入连接流程，并加连接锁，避免重复点击导致多个连接任务并发执行。
3. 后端扫描本机串口列表。
4. 串口会先过滤 CH340 设备。
5. 对候选串口进行波特率识别。
6. 波特率识别不是只看串口能否打开，而是做双重判断：
   - 检测数据帧分隔符。
   - 校验后续帧长度是否符合支持范围。
7. 找到正确波特率后，先关闭检测串口，再用稳定连接流程重新打开。
8. 稳定连接带重试机制：
   - 最多重试 3 次。
   - 每次连接有超时时间。
   - 失败时归一化为明确错误码和用户提示。
9. 连接成功后，读取设备 MAC。
10. 根据 MAC 解析设备类型：
    - 优先查本地缓存。
    - 缓存没有时再走在线或配置解析。
11. 解析成功后，把串口对象、设备类型、MAC、波特率、最近数据时间写入全局状态。
12. 后端绑定串口数据监听器，进入实时接收阶段。

## 4. 实时数据解析与质量判断

1. 串口收到原始字节数据后，先按协议分帧。
2. 根据不同设备类型，把原始点位转换为矩阵数组 `arr`。
3. 对矩阵做基础校验：
   - 数据必须是数组。
   - 点数必须符合当前设备的矩阵尺寸。
   - 点值必须可转换为数字。
4. 校验失败时，不直接当作正常数据推送，而是写入数据质量状态。
5. 数据质量逻辑会记录：
   - 总帧数。
   - 坏帧数。
   - 连续坏帧数。
   - 坏帧比例。
   - 最近一次错误原因。
   - 采样频率是否异常。
6. 如果连续坏帧过多或矩阵尺寸错误，会标记为 `device_error`。
7. 如果只是短时间不稳定，会标记为 `degraded`。
8. 如果超过在线阈值没有收到新数据，会标记为 `offline`。
9. 实时数据对象会包含：
   - `status`。
   - `arr` 矩阵数组。
   - `HZ` 或采样频率。
   - 原始帧元信息。
   - 矩阵尺寸元信息。
   - 数据质量信息。
10. 后端按当前频率定时执行 `colAndSendData`，负责发送实时数据，也负责采集时入库。

## 5. 数据方向、归零与入库处理

1. 用户在前端设置翻转或旋转方向后，会调用 `/setDataDirection`。
2. 后端把方向配置保存为 `data_direction.json`。
3. 方向支持：
   - 左右翻转。
   - 上下翻转。
   - 90、180、270 度旋转。
   - 多矩阵系统按 `${system}-back`、`${system}-sit` 分别保存方向。
4. 后端保存采集数据前，会先按当前方向处理矩阵。
5. 方向处理顺序是：
   - 先按 90 度倍数旋转。
   - 再做左右翻转。
   - 再做上下翻转。
6. 如果开启归零，后端会用当前矩阵减去归零基线。
7. 减完后小于 0 的值会归为 0。
8. 入库时会过滤无效数据：
   - 离线数据不入库。
   - `device_error` 数据不入库。
   - 非对象数据不入库。
9. 入库数据会补充业务元信息：
   - 设备 MAC。
   - 设备类型。
   - 软件版本。
   - 压力单位。
   - 方向信息。
   - 归零信息。
10. 最终写入 SQLite 的 `matrix` 表，字段包括数据 JSON、时间戳、采集名称、框选信息。

## 6. 前端实时接收、计算与渲染

1. 前端通过 `useWebSocket` 建立 WebSocket 连接。
2. WebSocket 固定 3 秒重连。
3. 前端兼容两种消息格式：
   - JSON。
   - MessagePack 二进制。
4. 收到消息后按字段分发：
   - `sitData` 是实时数据。
   - `sitDataPlay` 是回放数据。
   - `contrastData` 是对比数据。
   - `macInfo` 是设备信息。
   - `dataQuality` 是数据质量事件。
   - `connectProgress`、`connectResult` 是连接过程事件。
5. 实时矩阵进入 `useMatrixData` 处理。
6. 前端会根据当前系统类型匹配矩阵配置。
7. 对 `endi` 类型数据，会限制显示值上限为 255。
8. 如果用户做了框选，前端会把框选坐标转换为矩阵范围。
9. 框选支持多区域，每个区域单独提取数据。
10. 没有框选时，默认使用整张矩阵。
11. 前端会计算压力统计：
    - 总压力。
    - 有效面积。
    - 最大压力。
    - 最小压力。
    - 平均压力。
12. 前端会计算压力中心和分布指标：
    - 重心坐标。
    - 均值。
    - 方差。
    - 偏度。
    - 峰度。
    - 正态分布曲线数据。
13. 不同系统会做单位换算：
    - `endi-back`、`endi-sit` 使用对应换算函数。
    - `carY` 类型按固定除数换算压力。
14. 处理后的数据进入状态管理，再驱动：
    - 2D 数值矩阵。
    - 3D 压力点阵。
    - ECharts 曲线。
    - 侧边统计面板。

## 7. 历史数据、回放与对比处理

1. 用户开始采集时，前端调用 `/startCol`。
2. 后端设置采集名称、方向、采集状态。
3. 采集过程中，实时定时器继续推送数据，同时把有效帧写入数据库。
4. 用户结束采集时，前端调用 `/endCol`。
5. 后端关闭采集状态，但实时展示仍可继续。
6. 历史列表通过 `/getColHistory` 查询数据库。
7. 用户选择某条历史数据后，前端可请求：
   - 历史详情。
   - 框选后的历史数据。
   - 回放。
   - 对比。
   - 报告数据。
8. 回放开始时，后端把历史帧加载到内存。
9. 回放按当前播放速度定时取帧。
10. 每一帧回放前都会校验：
    - 是否有矩阵。
    - 矩阵长度是否正确。
    - 点值是否为数字。
11. 坏帧会被跳过，并累计跳帧数量。
12. 回放帧通过 WebSocket 推送为 `sitDataPlay`。
13. 拖动进度条时，后端根据索引生成当前帧快照。
14. 对比功能会读取两组历史数据。
15. 对比前会校验：
    - A、B 不能是同一条记录。
    - 两组数据不能为空。
    - 两组矩阵类型必须可比较。
    - 矩阵尺寸必须一致。
16. 对比结果包含：
    - A 帧。
    - B 帧。
    - 差值帧。
    - 当前进度和时间戳。
17. 同一条记录的时间点对比要求至少有两帧数据。

## 8. CSV 导入、导出与文件处理

1. 用户导出数据时，前端调用 `/download` 或 `/downlaod`。
2. 后端根据历史记录、字段配置、框选信息生成 CSV。
3. 导出路径优先使用用户设置的下载目录。
4. 如果没有设置，使用 Electron 传入的系统下载目录。
5. 后端会确保目标目录可写。
6. 导出字段支持按配置选择，避免固定写死所有字段。
7. 用户导入 CSV 时，前端调用 `/uploadCsv`。
8. 后端先保存上传文件到临时位置。
9. 保存后立即校验 CSV 结构。
10. 校验内容包括：
    - 必须包含基础时间字段。
    - 必须包含矩阵数据字段。
    - 统计列和矩阵列结构要符合系统导出格式。
    - 矩阵长度必须匹配支持尺寸。
    - 矩阵元素必须是数字。
11. 校验失败时，后端删除临时文件，并返回“数据有误”。
12. 校验成功后，前端把导入文件加入本地导入列表。
13. 导入列表按文件路径去重。
14. `/getCsvData` 读取 CSV 时，会等待解析完成，再转换为回放可用的数据结构。
15. 导入 CSV 可以复用回放和展示链路，不需要单独做一套渲染逻辑。

## 关键处理链路汇总

```text
Electron 启动
  -> 分配端口
  -> 启动后端子进程
  -> 后端读取配置
  -> 初始化 SQLite
  -> 启动 API 和 WebSocket
  -> 加载前端页面

用户连接设备
  -> 扫描串口
  -> 过滤 CH340
  -> 检测波特率
  -> 稳定连接
  -> 读取 MAC
  -> 解析设备类型
  -> 绑定数据监听

实时数据
  -> 原始字节分帧
  -> 协议解析
  -> 生成矩阵 arr
  -> 校验矩阵尺寸和数据质量
  -> 应用方向
  -> WebSocket 推送
  -> 前端统计计算
  -> 2D/3D/曲线渲染

采集数据
  -> 开始采集
  -> 实时帧过滤
  -> 应用方向
  -> 应用归零
  -> 补充元信息
  -> 写入 SQLite
  -> 结束采集

历史数据
  -> 查询采集记录
  -> 加载历史帧
  -> 校验坏帧
  -> 定时回放或按索引取帧
  -> WebSocket 推送
  -> 前端复用实时渲染逻辑

数据对比
  -> 读取 A/B 记录
  -> 校验矩阵类型和尺寸
  -> 对齐帧索引
  -> 生成 A/B/差值帧
  -> 前端展示对比结果

CSV
  -> 导出时按字段配置生成文件
  -> 导入时校验结构和矩阵
  -> 合法数据转换为可回放帧
```
